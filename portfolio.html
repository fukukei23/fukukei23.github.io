AI生成コードの罠と品質担保プロセス — 実例による検出機構

テスト全緑・CI全緑なのに、本番の定期処理が1件も動いていなかった

発見 — 何が起きていたか

  • 対象: BUYMA販売管理システム（Flask + Celery + Redis・37,000行超）
  • テスト2,000件超が全て緑・CIも緑の状態で、Celeryワーカーのタスク登録が0件。価格監視の定期実行が4時間ごとに無音で失敗し続けていた（タスク登録漏れ + タスク名不一致の二重の不整合）
  • テストが緑の理由: テストは関数を直接呼ぶだけで、「ワーカーがそのタスクを登録しているか」を検証していなかった
  • 1度目の包括レビューはこのバグを見逃し、翌日の独立した2度目のレビューで発見
  • 見つけたのはコード読解ではなく「1度目で終わらず、自分に2度目の独立レビューを課す」運用ルール——AIレビューを鵜呑みにせず重ねることで、機能停止級の欠陥を拾い上げた

対策 — どう検出し、どう直したか

  • 独立レビューを重ねる: 異なるセッション/異なるLLMに独立レビューさせる。指摘は検証コマンドに変換して実測結果だけで採否（誤った指摘はgrep実測で参照0件を確認し却下）
  • 修復: ワーカーのタスク登録を修正し、「定期実行の全タスク名がワーカーに登録済みか」をassertする回帰テストを新設——同じ失敗が再び「緑」に隠れないようにした
  • 記録: 発見から修復までの判断過程をナレッジベース（判断記録1,300+件）に保存し、同じ失敗モードの再発防止に再利用
Python / Flask / Celery / Redis 複数LLM独立レビュー 実測裁定 回帰テスト新設 判断記録
💡 AIにコードを書かせる開発で最も危険なのは「検証が通ったように見える」こと。個別のバグよりも、AIの出力を鵜呑みにしない検出機構（独立レビュー × 実測裁定 × 記録）を開発プロセスに組み込むことを主眼にしています。

AI生成コードの罠と品質担保プロセス — 実例による検出機構

テスト全緑・CI全緑なのに、本番の定期処理が1件も動いていなかった

発見 — 何が起きていたか

  • 対象: BUYMA転売管理システム（Flask + Celery + Redis・37,000行超）
  • テスト2,000件超が全て緑・CIも緑の状態で、Celeryワーカーのタスク登録が0件。価格監視の定期実行が4時間ごとに無音で失敗し続けていた（タスク登録漏れ + タスク名不一致の二重の不整合）
  • テストが緑の理由: テストは関数を直接呼ぶだけで、「ワーカーがそのタスクを登録しているか」を検証していなかった
  • 1度目の包括レビューはこのバグを見逃し、翌日の独立した2度目のレビューで発見
  • 見つけたのはコード読解ではなく「1度目で終わらず、自分に2度目の独立レビューを課す」運用ルール——AIレビューを鵜呑みにせず重ねることで、機能停止級の欠陥を拾い上げた

対策 — どう検出し、どう直したか

  • 独立レビューを重ねる: 異なるセッション/異なるLLMに独立レビューさせる。指摘は検証コマンドに変換して実測結果だけで採否（誤った指摘はgrep実測で参照0件を確認し却下）
  • 修復: ワーカーのタスク登録を修正し、「定期実行の全タスク名がワーカーに登録済みか」をassertする回帰テストを新設——同じ失敗が再び「緑」に隠れないようにした
  • 記録: 発見から修復までの判断過程をナレッジベース（判断記録1,300+件）に保存し、同じ失敗モードの再発防止に再利用
Python / Flask / Celery / Redis 複数LLM独立レビュー 実測裁定 回帰テスト新設 判断記録
💡 AIにコードを書かせる開発で最も危険なのは「検証が通ったように見える」こと。個別のバグよりも、AIの出力を鵜呑みにしない検出機構（独立レビュー × 実測裁定 × 記録）を開発プロセスに組み込むことを主眼にしています。

Heartbeat
OpenClawで3層構成: 1分（緊急監視）/ 5分（設定検知）/ 30分（会話スキャン）。「フクロウ」VPSがDiscord経由で「よつば」ローカルPCを監視する死活監視の仕組みで、本ポートフォリオ「止めずに保つ運用」の技術的中核。
JASRAC / NexTone
SHOWROOM楽曲報告自動入力ツールの受託案件で対象とした2大著作権管理事業者。楽曲コードの頭文字からJASRAC/NexTone欄を自動振り分け・50件上限で自動停止・空行自動削除のフェイルセーフを実装。ココナラ経由で受注・納品済み・顧客満足（2025年12月）。
Stripe
reserve-optimizer（LINE予約システム）の決済基盤として組み込み。LINE Bot → Stripe Checkout → 予約確定のフローをCloudflare Workers経由で接続し、月額保守サービス（ココナラ出品）の決済にも拡張予定。
Cloudflare Workers
reserve-optimizerのリクエスト処理層として採用。アクセスが少ないサービスなら実質無料で運用できる特性を生かし、LINE BotからのWebhook受信 + Stripe API呼び出し + DB書込みをWorkers上で実行する構成。
OAuth1
X（旧Twitter）自動投稿パイプラインで永続化層として使用（OAuth1.0a + Twitter API v1.1・署名キー暗号化保存）。信頼度自動承認ロジックと組み合わせ、72h SLAでX投稿を無人運用する設計・非公開リポジトリで開発中。
RAG
ssot-search v2として実装（数値マスター.md正典）。Phase 0-5完走・4,021文書 / 24,010チャンク / ruri-v3埋め込み + ChromaDB保管 / 30分毎の差分インデックス更新 / 外部LLM生成テストセット39問による3条件精度評価（Recall@5 0.026→0.744）。
ChromaDB
ssot-search v2のベクトル保管庫として採用。`update_rag_index.sh`が30分毎にobsidian-ssotの差分をスキャンしてChromaDBに書き込む設計。日本語埋め込みは cl-nagoya/ruri-v3-130m を使用（JMTEB比較で選定）。
ハイブリッド検索
ssot-search v2でベクトル検索（意味の近さ）と字句検索（キーワード一致）をRRF（Reciprocal Rank Fusion）で統合。単独よりも取りこぼしが少なくなることを実測で確認。設計経緯は`01_DECISIONS/ssot-search-v2/`配下のPhase記録に残す。
Recall@5
ssot-search v2の精度指標。v1（grep+BM25相当）でRecall@5=0.026・v2（RAG+ハイブリッド）で0.744に改善。テストセットは外部LLM（MiniMax M3）が自動生成・採点基準は事前固定・ベンチ詳細は`01_DECISIONS/ssot-search-v2/2026-08-17_Phase3+4精度評価ベンチ完了-3条件比較とRRF統合MRR低下の正直な記録.md`が正典。
